## 0. 给读者：使用规则与限制（先读这一节）

**这是什么**：一个独立的对话框。员工可以直接打字、贴上文字，或上传一份 Excel，请 AI
帮忙整理成系统读得懂的内容。AI 提出的每一项改动，最后都要由**登录的员工逐项确认**，
再经现有的核对与合并流程才会写入。

**一句话原则**：AI 只提出建议；写入永远由人按下确认，记在那个人的名下，
并注明这次写入有 AI 协助。

| 可以 | 不可以 |
| --- | --- |
| 读一份格式不明的表，指出哪一栏可能是什么 | 新增或推测大厦、楼层、单位、坐标、人员、日期、期限 |
| 把口语描述整理成到访记录的草稿，等你确认 | 直接写入、覆盖或删除任何资料 |
| 处理整份附件（所有工作表、所有行），不只前几行 | 跳过确认，或把部分结果包装成全部成功 |
| 指出同一批资料里可能重复的项目，请你核对 | 只凭内容相同就自动合并，或断定是两次不同探访 |
| 把已确认的内容排成导入预览 | 绕过格式识别、栏位核对或合并预览 |
| 回答与外展记录、本系统、Excel 整理有关的问题 | 回答其他话题（固定回复「與本項目無關，無法回答。」） |
| 解释它为什么这样对应 | 当成官方数字、完成比例，或医疗／法律判断 |

**每次都要经过的三道闸门**（2026-10-24 阶段 5 改写）

1. 平台管理员已为这个机构开启 `aiAssistant`（**按机构、默认关闭**；机构管理员只能看，不能切）。
2. 本系统服务器代理检查通过：登录会话有效、账号属于该机构、请求在限流与大小上限之内、
   服务器已配置 Azure key、请求通过服务器端的话题闸门。**任何一项不过，服务器不会向 Azure 发出请求。**
3. 按下「確認並執行」之前，目标清单完整列在画面上：在哪儿新增什么、哪几行不会写入与原因。
   文件另在送出前写明总行数与栏数，看起来是姓名、电话的栏**自动不送**（内容仍留在裝置、写进備註）。

> **机构密语不再是 AI 的前提**（阶段 5）。钥匙只放在服务器，员工不需要解锁密语才能用 AI。
> 但**读工作区资料仍然要先解锁**——那是工作区本身的加密，与 AI 无关。

**写进去的东西记在谁名下**：新增记录的 `createdBy`、跟进事件的 `operator`、撤回的
`deleted.by` 一律是**当时登录的账号**，服务器逐条核对，不能冒名，AI 也不能代替。
员工能改不能删；删除、清空、撤回别人的记录仍然只有管理员可以做（`CLAUDE.md` 3.5）。
凡经 AI 协助的写入，另带一个明文标记，**机构管理员在操作记录与记录详情里都看得到**（第 6.3 节）；
阶段 5 起这个标记由服务器发号（`requestId`）并在写入时核对，不再只是客户端的声明。

**限制（先讲清楚，免得期待落差）**

- **只有 Azure OpenAI 一家供应商**，端点和模型由服务器配置，**界面不能改、请求不能指定**
  （第 4 节）。任何供应商都不允许浏览器直连。
- 请求路径是：**你的浏览器 → 本系统服务器 → Azure**。服务器进程**看得到请求与回应的内容**，
  这是本次架构变更的明确代价；换来的是 key 不出服务器、开关关闭时真的不出站。
  服务器承诺**不落库、不写内容日志、`store:false`**（第 5、9 节）。
  Azure 侧仍按资源条款处理（含内容筛选与滥用监控），**不等于「没有人看得到」**，不要这样写。
- **附件是整份处理的**：所有行都会经过服务器与 Azure，不再只送前 20 行样本。选好文件后，
  同一屏写明总行数与栏数；看起来是姓名、电话的栏自动不送。按下「整理這份表」就是你同意的范围。
- 读取器上限仍是：`.xlsx`、5 MB、每张工作表 5000 行、64 栏（[readWorkbook.ts](../src/data/readWorkbook.ts)）；
  服务器另有更小的**单次请求上限**（行数、字节数），超出要分块送出，界面要讲清楚，不能静默截断。
- 对话与附件**不存到服务器**；对话本身不进审计库，也不会随导入或导出文件带出去。
  审计只记元数据：谁、哪个机构、哪个模型、耗时、状态码、请求 ID、行数／块数、token 数。
- AI 会出错：可能看错栏、漏掉一栏、把两行当成同一笔。所以才有第 3 点——发现它错就直接改，
  不要照单全收。
- **费用在 Azure 侧看**。所有机构共用同一把服务器 key，服务器可以按机构记估算用量，
  但那不是帐单；额度隔离与上限见第 12 节。
- **只用合成资料测试 AI 路径**。按 `CLAUDE.md` 第 2 节的「真实资料两步走」，第一步本来就
  不录姓名、电话等能认出个人的资料；AI 路径也只应处理这一步范围内的内容。

## 1. 要解决的三件事

| 需求 | 现况 | 目标 |
| --- | --- | --- |
| 非既定格式的 Excel 也能读进来 | 规则识别器只认 `src/imports/profiles.ts` 的清单，清单外一律拒绝（[detector.ts](../src/imports/detector.ts)） | AI 提出「哪一栏是什么」的**建议**，由人确认目标清单后，走现有的核对与合并流程 |
| 每天知道要做什么 | 待跟进清单只在 Excel 的「待跟进」页，要自己翻 | 侧边栏「任務提醒」入口＋逾期／今日角标，按逾期／今日／即将到期／之后／未排期分组，可跳到对应位置；也可以在 AI 助手对话框直接问（本机计算，不送出去） |
| 不要变成通用聊天机器人 | 尚无 AI 对话入口 | 对话框与服务器代理各有一道话题闸门，与本项目无关的问题直接拒绝；回复只能是「提案」，不是资料 |

**AI 只做栏位对应、记录草稿与措辞建议，不做业务判断**：不新增或推测大厦、楼层、单位、坐标、人员、日期。
表格写到而工作区没有的楼层／单位，只由对话框**列入目标清单**、人在按下「確認並執行」时一并同意后才按既有「編輯結構」的规则建立（第 6.1 节）；
大厦永远不代建——一张表给不出地图位置。所有数字、清单、到期日一律由 `src/domain/` 的既有函数算出，AI 不得改写。

**有 AI 参与就要说清楚**：哪一条记录是 AI 帮忙整理的，机构管理员要一眼看得到（第 6.3 节）。
不是为了让管理员逐个审批，而是事后能回答「这批资料是 AI 对的还是人对的」。
阶段 5 起这句话可以答得更实：服务器发的 `requestId` 可以核对，不必只靠员工自述。

### 「看不到」现在是什么意思

阶段 5 起，key **只存在于服务器进程的环境变量里**：

- 浏览器拿不到，所以开发者工具里没有；构建产物里也不该有（`VITE_` 前缀绝对不能出现）。
- 服务器不把它写进数据库、审计、日志、错误响应，也不在状态接口里返回。
- 机构管理员只能看到「AI 助手：已启用／未启用，供应商 Azure OpenAI，模型 …」，
  **没有 key 输入框、没有删除按钮、没有显示／复制**。

这**不再是**「密码学上防住员工」的问题，因为员工端根本没有可拿的东西。
风险转移到三个新地方，必须一起管理：

1. **服务器与运维**：能登录 VPS、读 `.env` 或读取进程内存的人，就能拿到 key，也能看到经过的请求内容。
2. **日志**：Node、反向代理、错误处理、APM 任何一处把 body 写下来，都等于把住户文字落盘（第 9 节）。
3. **额度**：所有机构共用同一把 key，一个机构用量失控会拖累其他机构（第 12 节）。

### 历史（阶段 1–4，已被取代）

阶段 1–4 的作法是：key 用机构资料钥匙封装，服务器只存 `sealed_key`，同机构任何成员
都能取回密文、在本机解开、**由浏览器直接呼叫供应商**；`aiAssistant` 由机构管理员切换；
员工在技术上拿得到明文 key，这一点当时是明确接受的取舍。
**这些都不再成立**：`docs/ENCRYPTION.md` 不适用于 AI 请求（见第 9 节与附录 A 第 5 项），
`server/orgAi.mjs` 的密封密钥路径、`src/ai/credential.ts` 的内存 key 都将在阶段 5 停用。

## 4. 供应商：Azure OpenAI 唯一（2026-10-24 重写）

**只有一家**。不是白名单里的第一家，而是**唯一**一家：

| 项 | 规则 |
| --- | --- |
| 供应商 | Azure OpenAI（与照片回录同一套资源） |
| 端点 | 服务器环境变量 `AZURE_OPENAI_ENDPOINT`，启动时校验：必须 `https:`、无账号密码、无 query／hash、路径为 `/openai/v1` |
| 主模型 | `AZURE_OPENAI_DEPLOYMENT`（建议 `gpt-6-luna`） |
| 备用模型 | `AZURE_OPENAI_FALLBACK_DEPLOYMENT`（建议 `gpt-6.1-sol`）；留空＝不切换 |
| key | `AZURE_OPENAI_API_KEY`，只存在于服务器 `.env` |
| 请求格式 | `POST {endpoint}/responses`，`store: false`，结构化输出（`text.format` 的严格 JSON schema） |
| 浏览器直连 | **任何供应商都不允许**。前端没有端点、没有 key、没有 `model` 参数 |

**为什么收敛到一家**：

- 服务器代理后，「哪家供应商允许浏览器直连」这个问题消失了；CORS 不再是选型条件。
- 只有一家，才能把「端点在服务器、模型在服务器、key 在服务器」这条边界写死，不给请求留自订空间。
- 与照片回录共用同一个 Azure 资源与 key，运维只有一套配置；代价是额度也共用（第 12 节）。

**请求不能带的东西**：`model`、`store`、`endpoint`、`api-key`、`temperature` 以外的供应商参数、
以及任何指向别的模型的字段。带了就 `400`（不是静默忽略），免得前端以为换模型生效了。

**主备切换规则**

| 上游结果 | 处理 |
| --- | --- |
| `429`、`5xx`、逾时 | 切备用模型重试**一次**；仍失败则把最后一次的错误类别回给前端 |
| `401`／`403` | **不切换**——是 key 或配置的问题，换模型不会好；回「服务器设定有误」 |
| `400`（含内容筛选拒绝） | **不切换**；回「内容被安全筛选挡下」，不重试 |
| 输出不合 schema | 不切换；整份作废（与阶段 2 的契约规则相同） |

## 5. 密钥与代理（2026-10-24 重写）

### 5.1 key 只放在服务器

1. 运维在服务器 `.env` 设置 `AZURE_OPENAI_API_KEY`、`AZURE_OPENAI_ENDPOINT`、
   `AZURE_OPENAI_DEPLOYMENT`、`AZURE_OPENAI_FALLBACK_DEPLOYMENT`（沿用照片回录同一组变量）。
2. 服务器启动时读取并校验；**不写数据库、不写审计、不下发、不封装**。
   `.env.example` 只列变量名，`AZURE_OPENAI_API_KEY=` 留空。
3. 轮换＝改 `.env` → 重启进程。旧 key 立即失效；不需要清理数据库，也不需要通知各机构改设定。
   轮换属运维操作，**不进应用审计**（应用看不到 `.env` 的变更）；应用审计只记「谁在什么时候用了 AI」。
4. 未配置 key 时：状态接口回 `configured: false`；代理回 `503`，文案写明「AI 助手尚未由平台管理员配置」。
   开关即使开着也用不了，界面要直说，不能显示成可用。

**禁止**：`VITE_AZURE_*`、任何把 key 传进浏览器的接口、把 key 写进审计／日志／错误信息、
把 key 贴进 PR、issue、`log/` 或聊天。

### 5.2 服务器代理端（`server/aiProxy.mjs`，阶段 5 新增）

照 `server/photos.mjs` 的模式写：认证 → 开关 → 限流 → 闸门 → 代理 → 审计。

```
POST /api/ai/assist
  1. 会话有效、CSRF 正确（与所有写请求相同）
  2. features.enabled('aiAssistant', user.org_id)  → 关闭时 403，且不向 Azure 发请求
  3. 服务器已配置 key  → 否则 503
  4. auth.limit(`ai:${user.id}`) ＋ 每机构并发上限 → 超出 429
  5. body 大小、块大小（行数／字节）、模式白名单 → 超出 413／400
  6. 服务器端话题闸门 → 无关话题回 REFUSE，不调 Azure
  7. 组装请求：服务器自己的 system prompt、JSON schema、store:false、模型白名单
  8. 调 Azure；429／5xx／逾时切备用模型一次，401／403 与内容筛选不切
  9. 校验上游回应（结构、大小上限）、抽取 requestId 与 usage
 10. 审计只记元数据；返回 proposal ＋ aiAssist 元数据
```

**前端不能决定的事**：端点、模型、`store`、system prompt、JSON schema、超时、是否重试。
前端只能送「模式 + 资料」（第 6.1 节）。

**服务器端话题闸门**：前端可以被绕过（改 JS、直接打 API），所以服务器必须自己判一次。
闸门的固定回复文案与话题清单只维护一份（两端共用同一份常量，测试断言一致，
做法与 `SENSITIVE_FIELDS` 的两份清单相同），避免出现「前端拒绝、后端放行」或反过来。

**审计字段**（`ai_assist` 一类）：`user_id`、`org_id`、`kind`（mapping／draft）、
`model`、`fallback_used`、`duration_ms`、`status`、`request_id`、`rows`、`chunks`、
`input_tokens`、`output_tokens`。**不含 prompt、回应、文件名、表头、栏位值。**

## 6. AI 入口

### 6.1 独立对话框（流程保留，阶段 5 只改呼叫路径）

**为什么是对话框**：阶段 2 把 AI 面板放进「紙本與 Excel 工作台」，只在规则识别 `UNKNOWN`／`AMBIGUOUS`
时出现，终点必然是「导入一份文件」。实际使用时，人手上多数不是一份完整的活页簿，而是
「这张纸上的几行」、「这段口述」、「帮我把这栏拆开」——没有一个对应的文件可以导入。
所以入口是一个独立的对话框，文件只是其中一种输入。

**三步走、两屏**（2026-10-24 定为最终形态）：**输入 → 目标清单 → 按一次「確認並執行」**。

```
第一屏（输入）
员工在对话框：打字／贴上，或选一份 .xlsx（可拖放）
  · 打字／贴上 → 直接按「整理成目標」送出，清单在下一屏
  · 文件 → 本机先跑规则识别（detector.ts，不变）与整份读取，同一屏显示
           「共 N 行 · M 欄，將分 K 次送出」；姓名、电话等栏自动不送（内容仍在裝置）。
           按「整理這份表」才送出
        ↓
   浏览器 POST /api/ai/assist（只连自家服务器，一次一块）
        ↓
   本系统服务器 → Azure OpenAI（store:false）
        ↓
   服务器回传受限 JSON ＝ 提案（不是资料）
        ↓ 契约校验：不合规整份作废，不留部分结果
第二屏（目标清单，一列一件事）
     新增 裕安樓「9F」这一层与「9F A室」（第 4、5 行需要它）
     在 裕安樓 · 5F B室 新增 1 笔到访记录（第 2 行 · 2026-10-05 · 陳同事）
     不会写入的 2 行：列出行号与原因，不静默略过
        ↓ 栏位对应收在这个清单下面的折叠区，改对应会重新整理清单
   按下「確認並執行」：先建清单上的楼层／单位，再把文件重读一次，写入那些行
        ↓
   写入时盖登录员工的身份（createdBy／operator）与 AI 协助标记（aiAssist）
```

**已经没有「勾选」这一步**（2026-10-24 最终形态）：清单上每一件事都会执行，屏幕上没有
勾选框；人做的唯一决定是「按不按確認並執行」。这不是放宽——AI 仍然不能自己写，
清单仍然逐条列在眼前，不会写入的行仍然逐行列出行号与原因。

- **为什么取消逐行勾选**：勾出一堆默认选中的行，等于让人替 AI 复核它自己的解析，
  却没有一个「这样对不对」的判断依据；真正可核对的是「在哪幢、哪层、哪个单位、哪一天」
  这一句。逐行勾选只是把同一个确认拆成几十次点击。
- **疑似重复的行一律不写**，而且不会被列进清单（放在「不会写入」里并注明「疑似与…重复」）。
  没有稳定业务键时，内容相同既不证明是同一笔、也不证明是两笔（`CLAUDE.md` 3.2），
  所以要人先到记录历史或原表核对，确认后再走既有入口补录。
- **楼层／单位只在「建了它才能写入某一行」时才建**。表里提到、但对应行另外还缺日期或
  工作员的单位，不会为了「表里有」而建。
- **文字草稿**（口语整理）：清单显示「在哪新增 1 笔记录」，下面直接展开可逐项核对的记录内容；
  楼层／单位若工作区没有，同一条清单上会显示「新增…」，确认后一并建立。
- **为什么合并掉栏位核对与外送预览**：栏位对应是「怎么读这份表」的细节，不是人打开对话框
  要做的事；外送范围在文件选好那一屏已经写明，再按一次「確認送出」只是同一件事说两遍。

**整份输入，不是样本**（2026-10-23 改定；阶段 5 加服务器上限）：附件读进来后，AI 看得到全部行列。

- **按块送出**，每块的建议上限由服务器定（例如 400 行或 256 KB，取先到者），
  客户端按同一上限切块；每块回一份提案，最后汇成一个合并预览。
- 选好文件的那一屏写明「共 N 行 · M 栏，将分 K 次送出」；**总笔数和前后一致**，
  不得少送一部分却当成全部。服务器若发现块数与声明不符，整次拒绝，不拼接部分结果。
- **看起来是姓名、电话、备注的栏自动不送**：表头或整栏内容像个人资料的，送出前整栏留空，
  提案里标为「未送交 AI」，不得假装 AI 看过；这些栏的内容仍留在裝置，写入时原样记在備註。
- **服务器只做结构过滤，不做语义识别**：它只接受契约允许的栏位，未声明的栏位一律拒绝；
  但它**无法可靠判断**自由文字里有没有个人资料。所以「不送个人资料栏」的第一道防线仍在客户端，
  服务器是第二道（结构与大小），不是万能过滤器——不要对外宣称服务器会自动去识别个人资料。
- 读取器上限仍是 5 MB／5000 行／64 栏；超出要请人拆档，界面讲清楚，不能静默截断。
- 分块不改变结论：某行判不出来，就进 `NEEDS_REVIEW`，不会因为落在第 3 块而被跳过。

**对话框可以做**

| 做什么 | 产出 |
| --- | --- |
| 贴一段口述或纸本原话，整理成到访记录草稿 | 一笔待确认的观察事件，栏位值只取文字里有的 |
| 上传格式不明的表，问「哪一栏是什么」 | 栏位对应建议，收在目标清单的折叠区，可改 |
| 处理整份活页簿的所有工作表与所有行 | 分块处理，合成一份目标清单；不遗漏、不重复 |
| 指出「这几行看起来是同一户」 | **疑似重复**的行不写进目标清单，列在「不会写入」并注明与谁重复；不自动合并 |
| 把要做的每件事排成一行 | 目标清单：在哪儿新增什么；按下确认才执行 |

**对话框不可以做**

- 不新增或推测大厦、楼层、单位、坐标、人员、日期、期限；文字里没有就是没有。表格写到而工作区
  没有的楼层／单位，按下面「三处调整」处理：只列进目标清单，仍由既有结构编辑建立。
- 不直接写入 store：AI 的回复在型别上就是「提案」，没有任何路径可以跳过确认。
- **不原地改写既有记录**。要改已存在的观察事件，只能产生一条带 `correctsObservationId`
  的**追加更正**（`CLAUDE.md` 3.4）；原事件保留在历史里。
- 不删除任何东西。撤回、删楼层、清空工作区都只能由人在既有界面按，AI 最多提示「可以考虑撤回」。
- 不新增 canonical 栏位：只认 `src/imports/profiles.ts` 既有的集合。
- 不一次改多件事：一次回复＝一个提案，不得「顺便」建一幢大厦或补一个单位。
- 不回答与本项目无关的话题（客户端提示＋服务器闸门，回固定一句）。

**2026-10-24 三处调整**

1. **「AI 建議的欄位對應」只列 AI 认出的与必须的**。必须的栏位是 `buildingId`／`buildingName`、`occurredAt`、
   `worker`、`coverage`（与解析器自己的 `notes`、问题代码一致）；AI 认出或已经对上的栏位照常显示，必须项标「必須」。
   其余栏位折叠进「其他欄位（N）」，可展开手动指定——**不是删掉**，也**不要求逐栏确认**。
2. **表里写到、工作区没有的楼层／单位：列进清单，确认后建立**。`parseGenericRows` 遇到这种行不再直接判成无法写入，
   而是给该行 `NEEDS_REVIEW`，并输出一份 `pending` 清单（哪幢、哪层、哪个单位、哪几行）。对话框把**其中会让某一行
   变得可写入的**（`placesToCreate`）列为目标清单里的一条行动，按下「確認並執行」时由**既有的**
   `proposeLocation`／`applyLocationProposal`（即「編輯結構」同一套规则）建立，然后重新读整份文件、重新分类，
   再把清单上的行写入。
   - 只认数字楼层＋字母单位；「頂樓」这类读不出的写法仍然 `INVALID`，不猜。
   - 楼层名只是写法：表里写「5」或「5樓」，工作区写作「5F」，按楼层编号当作同一层
     （`readPaperFloor`／`floorNumber`），不会报成「找不到樓層」。同一个编号有两层时仍
     判为无法写入，不猜是哪一层。
   - **大厦从不代建**：缺大厦的行仍然 `INVALID`，因为大厦需要地图上的位置。
   - 建立前不写入任何东西；建立后该行仍要人确认；`features.structureEditing` 关闭时不提供建立入口。
   - 权限不因入口改变：仍是 `CLAUDE.md` 3.5 的「员工能改不能删」，由服务器逐条判定，界面只藏按钮不算。
   - 同一处不同写法（「9F / A室」与「9樓 / 9F A室」）只列一次；`pending` 的回归用例在
     `src/imports/genericRows.test.ts`（缺楼层、缺单位、同处合并、缺大厦、读不出的写法）。
3. **没有对上的栏不再要人逐栏勾选，也不让人逐栏剔走，一律原样记在備註**。`parseGenericRows` 新增
   `extraColumns`：没有 canonical 栏位对上的栏，每一行写入时把该栏的值原样写进 `note`
   （例如「原表「電話」：2111 1111」），并排在原有備註之后。对话框在目标清单的折叠区只**列出栏名**，
   写明「會記在備註」，没有勾选框。静默丢弃的真正防线是**原样保留到備註**：列出来、写进去，
   资料就还在，不需要人先做一次勾选或剔除的仪式。

**沿用阶段 2／3 已有的东西**：话题闸门的规则与固定回复、`src/ai/contract.ts` 的整份校验、
`src/ai/preview.ts` 的分块与行数合计、`src/ai/client.ts` 的错误分类（改为分类**服务器**的错误码）。
**阶段 5 新增的是「服务器代理」这一层**：端点、key、模型、`store:false`、限流、闸门、审计。

**要移除的（阶段 5）**：`src/ai/providers.ts` 的浏览器直连规格与 CORS 说明、
`src/ai/credential.ts` 的内存密钥、`GET /api/org/ai/key` 的客户端调用、
`AiSettingsPanel` 的 key 输入框。对话框、`aiPlan.ts`、`genericRows.ts`、`reminders` 都不动。

**对话内容只在本机**：不存服务器、不进审计、不进出口档。可另存一份本机「提案摘要」
（哪个文件、哪几栏由 AI 建议、人改了哪几栏），用途是事后能回答「这批资料是 AI 对的还是人对的」；
这份摘要不上传（是否要做见第 12 节）。

### 6.2 栏位建议与契约（阶段 2 建立，阶段 5 只改呼叫路径）

```
规则识别（detector.ts，不变）
 ├─ KNOWN ─────────────→ 原流程，完全不受影响
 └─ UNKNOWN / AMBIGUOUS
        ↓ 员工在对话框按「整理這份表」
   本机显示：总行数、栏数、分块数、不送出的个人资料栏
        ↓
   POST /api/ai/assist（服务器：开关、限流、闸门、模型白名单、store:false）
        ↓
   服务器 → Azure OpenAI → 受限 JSON
        ↓ 服务器校验结构 → 客户端再校验一次
   目标清单显示「AI 建议・待确认」＋理由
        ↓ 人看目标清单，按一次「確認並執行」
   现有 mergeWorkflow／appendObservations 写入
```

**输出结构（不合规整份作废，不给部分结果）**

```ts
{
  status: 'MATCH' | 'NO_MATCH' | 'REFUSE',
  sheetName?: string, headerRow?: number, profileId?: string,
  fields: [{ key: CanonicalField, columnIndex: number | null, confidence: number, reason: string }],
  unmappedColumns: [{ columnIndex, header: string, reason: string }],
  warnings: string[]
}
```

校验：`key` 必须在 `profiles.ts` 的既有栏位集合内；`columnIndex` 必须在范围内或 `null`；
出现多余栏位、缺必填栏位、越界索引 → 整份拒绝，提示改用人工对应。

**单一来源**：阶段 5 起，服务器持有 system prompt 与 JSON schema（因为请求由服务器组装，
不能让前端提供 schema 或提示词）。客户端 `src/ai/contract.ts` 保留一份边界校验，
防止传输或版本不一致；**测试要断言两边的栏位集合相同**（做法同 `SENSITIVE_FIELDS` 的两份清单），
不能各写一套然后慢慢漂移。

**不猜的红线**（沿用 `CLAUDE.md` 3.2／3.3）

- 缺日期、缺工作员、位置对不上 → 该行进 `NEEDS_REVIEW`，不补默认值、不猜。
- 没有稳定业务键 → 只标「疑似重复」，人工核对，不自动合并。
- 有内容但未对应的栏位 → 列出并阻止静默丢弃：原样写进该行備註，不要求人勾选或剔除。

**出错时要说明是哪一种**，不能一律「失败」（2026-10-24 改为服务器／Azure 的错误分类）：

| 情况 | 显示 |
| --- | --- |
| `503` 服务器未配置 key | 「AI 助手尚未由平台管理员完成設定，請稍後再試或聯絡平台管理員。」 |
| 服务器 `401`／`403`（key 被 Azure 拒绝） | 「AI 服務的伺服器設定有誤（金鑰被拒），請聯絡平台管理員。」**不要**叫员工去找机构管理员 |
| `429`（服务器限流） | 「送出太頻繁，請稍後再試；已送出的內容不會重複寫入。」 |
| `429`（Azure 额度／频率） | 「AI 服務已達額度或頻率上限，請稍後再試，或請平台管理員在 Azure 提高額度。」 |
| 内容筛选拒绝（`400`／`422`） | 「這份內容被 AI 服務的安全篩選擋下，未寫入任何資料；請改用人手對應。」 |
| 逾时（默认 60 秒，主备各一次） | 「等候太久，已取消；可再試一次或改用人手對應。」 |
| 服务器连不上 Azure（`502`／`504`） | 「AI 服務暫時無法連線，請稍後再試。」不透露内部地址与上游回应 |
| 输出不合 Schema | 「AI 回覆格式不正確，已作廢，未寫入任何資料。」 |

**历史（阶段 2 的边界，2026-10-23）**：阶段 2 把「外送预览 → 呼叫 → 整份校验 → 逐栏确认」
做齐，但确认后不写入，因为清单外的格式还没有解析器。阶段 3 补上了
`src/imports/genericRows.ts` 与 `appendObservations`，这个缺口已经不存在。
阶段 5 不改这条写入路径，只改前面的呼叫路径。

### 6.3 AI 协助的留痕（2026-10-24 阶段 5 重写「验证」部分）

**要回答的问题**：这条记录是人自己录的，还是 AI 帮忙整理的？机构管理员要能一眼看到，
而且不能只靠员工口头说明。

**怎么写**

- 记录的写入来源写在记录上，不是写在对话里：凡由 AI 提案、员工确认后写入的记录
  带 `aiAssist: { at, provider, model, requestId }`（**明文、结构栏位，不加密**）。
- `provider` 固定为 `azure-openai`；`model` 记**实际使用的模型**（主模型或备用模型，
  不能一律写主模型）；`requestId` 是服务器代理发出的那一次请求的编号。
- 更正记录（带 `correctsObservationId`）同样带标记；原记录不动。
- `createdBy`／`operator`／`deleted.by` 仍必须是登录者（`CLAUDE.md` 3.5），
  AI 标记**不能**替代这几个栏位，也**不能**用来改权限判定。
- `aiAssist` 写进去之后不能修改（现有 `server/workspaceAccess.mjs` 已拒绝），
  否则追溯就断了。

**服务器怎么验证（阶段 5 新增）**

服务器发过哪一次请求，它自己知道，所以可以真的核对，而不是只看声明：

1. 代理回应携带 `requestId`（优先用 Azure 回应的请求 ID；没有就由服务器生成并记录）。
2. 服务器在 `ai_requests(request_id, org_id, user_id, model, created_at, expires_at)` 记一行，
   只记元数据，**不记内容**；保留期建议 7 天，过期删除。
3. 工作区写入时，`assertAiAssist` 除了现有格式检查，再核对：该 `requestId` 存在、
   未过期、属同一机构、模型在服务器允许清单内。对不上 → 整批 `400`，不静默丢弃。
4. 同一机构内的同事可以共用提案例外**不开放**：`requestId` 与发起请求的账号绑定；
   管理员代录时仍须自己发起一次请求（或在阶段 5 实现前明确按「已声明」处理，见第 12 节）。

**这是披露机制，不是审批机制**：带标记的记录照样有效，不额外要求管理员批准；
它现在能防的是「说了但没发生」（伪造／过期／跨机构的 requestId），
仍然防不了「AI 真的用过但员工没标」——那要靠抽检与机构纪律。界面用词仍是「由 AI 協助」，
不是「已验证由 AI 产生」。

**看得到的地方**

| 位置 | 显示 |
| --- | --- |
| 记录详情／历史 | 「由 AI 協助（Azure OpenAI · gpt-6-luna · 2026-10-24 14:05）」＋登录者姓名 |
| 管理员的操作记录 | 每次合并若含 AI 协助记录，写一条 `ai_assisted_write`，对象是记录数与机构，**不含内容**；代理本身的元数据另记 `ai_assist` |
| 管理员筛选 | 可按「只看 AI 協助」筛出这批记录，方便抽检 |
| 导出 Excel | 增加一栏「AI 協助」（是／否），纸本回录与关联封存都带着它 |

**不记什么**：不记对话原文、不记 prompt／回应、不记被拒提案。token 数可以记在**审计元数据**里
（服务器现在看得到 `usage`），但它只是估算，不能当帐单。

## 7. 话题闸门

**目的**：AI 不是通用聊天入口。与香港社区外展、洗楼记录、本系统资料无关的问题，
一律回复固定文字，不尝试作答、不解释、不延伸。

**指定回复**（界面文案依仓库惯例用繁体）：

> 與本項目無關，無法回答。

**两道闸门，同一套规则**（2026-10-24）

| 位置 | 作用 |
| --- | --- |
| 客户端（`src/ai/scope.ts`） | 即时反馈；把使用者文字包成**资料区块**，不让它变成指令 |
| 服务器（`server/aiProxy.mjs`） | **真正生效的那一道**。前端可以被绕过，所以服务器必须自己判一次；无关话题直接回 `REFUSE`，不调 Azure |

- 两边的固定回复与话题清单只维护一份（共享常量），测试断言两处一致；
  不能出现「前端说无关、服务器照送」或反过来。
- **任务问题不经过闸门**（第 8 节）：它在本机由 `src/ai/reminderQuery.ts` 识别、由
  `src/domain/reminders.ts` 作答，没有任何内容送交服务器或 Azure。
- 系统提示由**服务器**持有并写死：只处理香港社区外展、劏房探访、本系统栏位对应与资料整理；
  其他话题一律拒绝。前端不能替换 system prompt。
- `REFUSE` 不算错误、不重试、不降级成别的模型硬答。
- 表格内容与使用者贴上的内容一律当**资料**，不当指令；单元格写「忽略以上指示」不得改变行为
  （有专门测试）。对话框的附件与贴上文字都要包在同一个资料区块里，不得插进系统提示。

## 8. 提醒（任务清单）

**计算在本机浏览器**。跟进文字与到期日是加密的，服务器要算就得解密，等于放弃加密承诺。
提醒因此既不经过服务器，也不调用 AI：不发 prompt、不用密钥，AI 助手开关关着也能用。
**服务器代理不影响提醒**：提醒仍然不出浏览器，阶段 5 没有改动这一节。

**两个入口，同一份答案**：

- 侧边栏页脚「任務提醒」→ 对话框，范围可切「今天 / 3 天 / 7 天 / 14 天 / 全部」；
- AI 助手对话框里直接问，例如「今天還有什麼未完成的跟進任務嗎？」。助手认出这是任务问题后，
  在本机算完直接列出，不联系服务器或供应商；问「所有未完成」给全部。万一认错（把一段记录当成问句），
  可按「這不是提醒，改為整理成記錄」把它当普通草稿送出去。

**答案里有什么**

| 项 | 来源 / 规则 |
| --- | --- |
| 逾期／今天／即将到期（默认 3 天）／之后／未排期 | `getOpenFollowUps` ＋ 香港时区日期；已撤回、已被后一条记录解决的都不算 |
| 日期 | 只用 `followUp.dueDate`；`timingNote` 只原样引用为「時間原話」，不换算成日期 |
| 指派 | `assignee` 精确等于登录者姓名（只忽略首尾空白）；不做模糊比对，职称或别名不算同一个人 |
| 员工（`MEMBER`） | 只列自己的任务，并写明「另有 N 項指派給其他同事、M 項未填負責人」；未指派的不算成自己的 |
| 管理员（`ADMIN`） | 全部打开的任务，逐条标出负责人；没填的写「未填負責人」 |

「今天」包含已逾期与未排期：两者都还没有做完，正是今天要看的东西。「明天」只回答明天，不把今天和
逾期的工作混进来。时区固定按香港，不跟装置时区走。

**范围设定**存在本机，不进机构同步（这是个人偏好，不是业务资料）。key 必须跟着机构与账号走，
否则同一部电脑上换人登录会沿用另一个机构的设定（`CLAUDE.md` 3.5 同一条规则）：

```
careflow-atlas.org.<orgId>.<userId>.reminders
```

没有登录账号（示范模式）用 `careflow-atlas.device.reminders`，不与任何机构混用。存的是
`{ days: 1 | 3 | 7 | 14 | null }`，`null` 是「全部」；读不出来就回到 3 天，不挡人。

**未做**：每日提醒时间、浏览器通知、分组开关、「只看指派给我的」开关（管理员目前看全部）、
每组最多显示 N 条（现在是滚动列表）。邮件、短讯、手机推送不做：没有 SMTP，服务器也读不到加密内容。

## 9. 安全与隐私边界（2026-10-24 阶段 5 重写）

这一节的前提变了，旧版「服务器看不到 AI 内容」的说法**不再成立**，不要在任何文案、PR 或对外说明里沿用。

### 9.1 数据流与可见范围

```
员工浏览器 ── HTTPS ──> 本系统服务器（Node） ── HTTPS + api-key ──> Azure OpenAI
                          │
                          ├─ 内存中有这次请求与回应（住户文字可能在内）
                          ├─ 不写数据库、不写内容日志、不写审计
                          └─ 只记元数据：谁、机构、模型、耗时、状态、requestId、行数、token
```

- **服务器进程必然看得到内容**，这是代理架构的定义，不是缺陷；不承诺「看不到」。
- 能读服务器内存、`.env`、进程 dump 或主机的运维人员，能够取得内容与 key。
  这是把风险从「每个员工的浏览器」集中到「一台服务器＋运维」的交换。
- **Azure 侧仍按 Azure 的资源条款处理**：内容筛选会在 Azure 端检查内容；`store:false`
  约束的是回应存储，**不等于** Azure 不留任何滥用监控记录。上线前要在 Azure 资源上确认
  滥用监控（abuse monitoring）设置与资料处理条款，并写进隐私条款；不要用「`store:false`＝不留痕」对外解释。
- **加密边界没有变**：工作区同步仍只在浏览器加密后才上传；AI 请求是**另一条路**，
  不加密、也不进 `org_workspaces`。所以 AI 内容不受 `docs/ENCRYPTION.md` 的加密承诺保护，
  必须在 `docs/ENCRYPTION.md` 里加一条「AI 代理例外」（附录 A 第 5 项，待定）。
- **资料范围**：按 `CLAUDE.md` 第 2 节「真实资料两步走」，第一步不录姓名、电话等可识别个人的资料，
  AI 路径只处理这一步范围内的内容。第二步（签隐私条款、开同步）之后要不要让 AI 处理姓名电话，
  需要重新决策，不能默认沿用。

### 9.2 服务器代理必须守住的承诺

| 承诺 | 实作要求 |
| --- | --- |
| 不落库 | 请求／回应只在内存；不写 SQLite、不写文件、不写对象存储 |
| 不写内容日志 | 不 `console.log` body；错误处理只记错误类别与状态码；不把上游回应写进错误信息 |
| `store: false` | 服务器组装请求时强制写入，客户端不能覆盖 |
| 审计只记元数据 | 第 5.2 节字段；**不含** prompt、回应、文件名、表头、栏位值 |
| 大小与时间上限 | body、回应、行数、并发、超时都要有上限；超出即拒绝，不截断后当成成功 |
| key 不泄漏 | 不进响应、审计、日志、错误、前端产物；`.env` 权限只给运行账号 |
| 端点固定 | 只接受启动时校验过的 `AZURE_OPENAI_ENDPOINT`；请求不能带 URL |
| 失败不降级成瞎猜 | 400／内容筛选／schema 不合不重试；429／5xx／逾时只切一次备用模型 |

### 9.3 仍然存在的风险

- **所有机构共用一把服务器 key**：额度、速率与故障互相影响；按机构记账只能到「估算」。
  隔离方案见第 12 节。
- **日志是最容易破功的地方**：Node 的异常堆栈、反向代理的 debug 日志、APM、
  甚至 `curl -v` 都可能带出内容。验收要用「实际跑一次，然后 grep 日志」来证明，不是靠口头保证。
- **公开仓库的 `log/`**：`CLAUDE.md` 第 9 节要求把每条发给 AI 的 prompt 原文记进 `log/`，
  而仓库是公开的。**应用运行时的 AI 日志**与**开发时的 prompt 日志**是两件事：
  前者默认关闭；后者若贴入了真实个人资料，一样是泄漏。开发与排障只能用合成资料；
  是否把 `log/` 移出版本库或改为脱敏摘要，列在第 12 节待定，不要单方面改掉现有约定。
- **CSP**：`deploy/nginx.conf` 目前没有 `Content-Security-Policy`。阶段 5 起浏览器只连自家服务器，
  加 CSP 时 `connect-src` **只需要 `'self'`**，不用再列任何供应商端点；服务器出站到 Azure
  不受浏览器 CORS 与 CSP 限制。旧的 CORS 注解要随之改写（附录 A 第 6 项）。
- **key 泄漏后的处置**：轮换 `.env` 并重启即可，所有机构立即改用新 key。
  这比旧的「逐机构换密文」简单，但也意味着一次事故影响所有机构。

## 10. 不做的事

- 不做 AI 自动写入、不做未经确认的合并。
- 不让对话框自己开一条写入路径；提案一律回到 `mergeWorkflow`。
- 不让 AI 原地改写既有记录（要改只能产生带 `correctsObservationId` 的追加更正），也不让它删除任何东西。
- 不让 AI 新增或推测大厦、楼层、单位、坐标、人员、日期、期限。
- 不因为「整份处理」就把全部内容静默送出：送出前写明行数栏数、个人资料栏自动不送、目标清单确认后才写入。
- 不把 `aiAssist` 标记当成权限依据或审批门槛；服务器核对 `requestId` 也不改变这一点。
- 不承诺「任何 Excel 都能读」。
- 不把 AI 摘要当成官方数字或完成比例。
- 不做邮件／短讯推送。
- **不开放自订 base URL、不让浏览器直连任何供应商、不让请求指定模型或 `store`**。
- **不把 key 放在前端、不加 `VITE_` 前缀、不提交进仓库、不贴进 prompt／issue／`log/`**。
- **不把 prompt 或回应原文写进应用日志、审计或公开的 `log/`**。
- **不用真实个人资料测试 AI 路径**；CI 不实际调用 Azure。
- **不宣称「服务器看不到 AI 内容」**，也不宣称「`store:false` 等于 Azure 不留任何记录」。
- **不在开关关闭时仍然尝试连 Azure**；关闭就是不发出站请求。

| 请求带 `orgId` 指向别间机构 | 服务器忽略并用自己的 `user.org_id`；不能借别机构的开关 |
| 浏览器 Network | 只有 `POST /api/ai/assist`；无 Azure 端点、无 `api-key` 请求头 |
| 构建产物 grep | 不含 `AZURE_OPENAI`、`api-key`、任何 key 形态 |
| `GET /api/org/ai/key` | `404`／`410`（接口已删除），不是 `200` |
| `PUT`／`DELETE /api/org/ai` | 已移除（`404`／`405`／`410` 之一，测试锁死） |
| 客户端请求带 `model`／`store`／`endpoint` | `400`；不能覆盖服务器设置 |
| 上游请求 body | 断言 `store === false`，`model` 是服务器配置的部署名 |
| 上游 `429`／`5xx`／逾时 | 切备用模型一次；最终失败时回 `502`／`504` |
| 上游 `401`／`403` | **不**切备用模型，回「服务器设定有误（金钥被拒）」 |
| 内容筛选拒绝 | 回 `422`，不重试、不切换、不写入 |
| 服务器限流 | 超限回 `429`，且不再调用 Azure |
| 请求超过 body／行数上限 | `413`／`400`，界面提示拆档或分块，不静默截断 |
| 未配置 `AZURE_OPENAI_API_KEY` | `503`；状态接口 `configured:false`；界面写明不可用 |
| 服务器端话题闸门 | 绕过前端直接打 API 问「今天天气」→ `REFUSE`，且不调用 Azure |
| 日志与审计 | 跑完一次完整请求后，grep 日志与审计表：**没有** prompt／回应原文、没有文件名与表头；只有元数据 |
| 错误响应 | 不包含上游 body、端点、key、堆栈 |
| 合成资料端到端（mapping／draft 各一次，mock Azure） | 目标清单 → 确认 → 写入；记录带 `aiAssist.provider`／实际 `model`／`requestId` |
| 伪造 `requestId` | 整批 `400` |
| 过期或别的机构的 `requestId` | 整批 `400` |
| 主备切换后的记录 | `aiAssist.model` 记**实际使用**的备用模型，不是主模型 |
| 员工写入带 `aiAssist` 的记录 | `createdBy` 是员工；员工不能删除它（现有 403 不变） |
| 管理员端 | 记录详情看得到「由 AI 協助（Azure OpenAI · 模型 · 时间）」；可筛选；`ai_assisted_write` 不含内容 |
| 导出 Excel | 「AI 協助」栏与记录一致 |
| 提醒 | 开关关闭时仍可使用；不产生任何网络请求 |
| 基线 | `npm run typecheck`／`lint`／`test`／`test:auth`／`build` 全绿 |

**一个 PR 只做一件事**（见第 13 节拆分）：阶段 5 至少拆成「文档」「服务器代理与开关」「前端去直连」
「日志与安全验收」「`aiAssist` 可验证」「清理旧数据」六件事，不要合成一个巨型 PR。

## 12. 仍待确认（2026-10-24 更新）

1. **多机构共用一把服务器 key 的额度与隔离**。要不要给每机构设每日上限（服务器侧）、
   要不要为 AI 单独开一个 Azure 部署以便分开计费与限速？现在的答案是「先共用，靠限流兜底」，
   但需要平台方确认这是可接受的营运方式。
2. **日志策略**。`log/` 目前随仓库公开、由 hook 自动记录开发期 prompt。
   要不要把 `log/` 移出版本库、或改为只记摘要？这与 `CLAUDE.md` 第 9 节直接冲突，必须由作者决定，
   本文档不单方面改。
3. **`store:false` 在 Azure `/openai/v1` 的兼容性与滥用监控设置**。上线前在真实资源上实测一次，
   并把「Azure 可能保留滥用监控记录」写进隐私条款；不要只用官方文档推断。
4. **模型部署名确认**：`gpt-6-luna`／`gpt-6.1-sol` 是否就是给 AI 助手用的部署；
   与照片回录共用同一部署是否合适（并发与额度会互相影响）。
5. **`aiAssist` 的验证强度**：本文件定为「服务器发 `requestId`、写入时核对」。
   要不要再加签名（HMAC）或绑定到具体记录内容？签名能防重放，但实现与清理都更重。
6. **旧 `org_ai_settings.sealed_key` 的清理时点**：先停用还是一并 drop；审计历史是否保留。
7. 提醒的默认窗口定 3 天是否合适，或应依机构习惯调整。
8. **对话框能碰到哪些既有资料**。目前定为「只产生新增与追加更正，不删除」；
   要不要允许「改电话、改错字」这类直接修改，需要先想清楚它在对话里怎么呈现成可核对的差异。
9. **对话纪录要不要留在本机**。倾向不留，或只留到登出为止。
10. **一次可不可以多个附件**（例如整批纸本扫描改成的多份 Excel）。现在定为一个附件、
    该附件的全部工作表都处理。
11. **`aiAssist` 要不要更细**：只记「有 AI 协助」，还是记到「哪几栏由 AI 建议、员工改了什么」。
12. **AI 是否只服务「真实资料第一步」**。第二步（含姓名电话）开启后，是否允许 AI 处理，
    需要机构与平台一起定，不能默认沿用现有开关。
