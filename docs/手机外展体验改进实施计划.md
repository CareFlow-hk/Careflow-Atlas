## 1. 总体判断

这 9 项不能只用一份手机 CSS 完成，实际分为四类：

1. **手机交互与布局**：地图优先、底部抽屉、触控多选、新增大厦面板、保存提示不遮挡（需求 1、2、5、6）。
2. **同一份搜索结果驱动清单与地图**：本地楼宇搜索规范化、结果联动、目标突出（需求 3、4）。
3. **统一业务口径**：明确记录「今次未能判断」、劏房拆分后的当前可走访单位统计（需求 7、8）。
4. **让保存／同步状态说真话**：先确认本机保存，再等服务器确认后才声称其他设备可见（需求 9）。

实施遵循四条原则：

- **手机与桌面共用数据、领域规则和保存路径**，不另写一套手机业务逻辑。
- **先改最影响现场工作的地图和多选**，再改搜索与连续走访，最后处理记录口径和同步反馈。
- **一个 PR 只做一件可独立验收的事**，避免把布局、领域统计和同步状态混成一次大改。
- **不扩大外部服务范围**：首页搜索已建档楼宇完全在本地完成，不调用 ALS，不新增功能开关，不把名称相似当作同一楼宇的身份证明。

## 3. 目标结构

### 3.1 手机工作区

手机断点沿用现有的 `760px` 边界，桌面布局保持不变。**采用一个三档底部抽屉，不做多个分别拖拽的面板**：多个拖拽区域会互相争夺滚动手势，也会让用户不知道下一步该拖哪里；一个抽屉更能保持地图、选户和记录的位置关系。

#### 三档停靠状态

| 档位 | 建议高度 | 主要用途 | 地图表现 |
| --- | --- | --- | --- |
| `collapsed` | 约 64px＋底部安全区 | 显示「樓宇清單」入口、当前楼宇摘要和上拉箭头 | 占绝大部分屏幕 |
| `half` | 约 50–55dvh | 搜索清单、选楼／层／单位、多选核对、查看历史 | 上半部仍可见，保持原位置 |
| `expanded` | 工作区可用高度的约 90–92%，顶部只留少量地图背景；总高度仍受顶栏和安全区约束 | 写具体记录、批量核对、较长的记录编辑表单 | 保持挂载但基本被覆盖 |

```text
收起：看地图                         半屏：找楼／选户
┌──────────────────────────┐        ┌──────────────────────────┐
│ MapLibre 地图            │        │ MapLibre 地图            │
│                          │        │                          │
│                          │        ├──────────────────────────┤
│                          │        │ ⌃ 把手／当前楼宇         │
├──────────────────────────┤        │ 清单或楼／层／单位详情   │
│ ⌃ 樓宇清單               │        │ 多选摘要／记录入口       │
└──────────────────────────┘        └──────────────────────────┘

展开：写记录
┌──────────────────────────┐
│ ⌄ 把手                   │
│ 当前楼／层／单位［更改］ │  ← 同一个紧凑 sticky 上下文块
│ 已选户 chips（如有）     │  ← 批量选中户并入此块，不另起面板
├──────────────────────────┤
│ 记录表单                 │  ← 一个主滚动区，不嵌套两张长滚动面板
│ 跟进与备注               │
│                          │
├──────────────────────────┤
│ 保存／取消               │  ← sticky 操作栏＋安全区，不被提示遮挡
└──────────────────────────┘
```

建议抽出小型、无业务语义的 `MobileSheet`／`useMobileSheet`，只负责：

- `collapsed` / `half` / `expanded` 三档状态；拖动时跟手，松手后按距离和速度吸附到最近档，不停留在任意尴尬高度；
- 把手同时有明确的小箭头：上拉／点按从收起到半屏，再上拉／点按到近乎全屏；展开后向下箭头回半屏，并有非手势的「收起」途径；
- `aria-expanded`、`aria-controls`、随档位变化的可访问名称、键盘操作和焦点返回；所有手势都有按钮等价操作，动画遵守 `prefers-reduced-motion`；
- Pointer Events 与 pointer capture；只在把手／非交互标题区设置拖拽所需 `touch-action`，内容区保留正常 `pan-y`，不在清单、单位格、输入框或整个表单上全局拦截；
- `100dvh`、安全区 `env(safe-area-inset-bottom)`、横屏及软键盘情况下的可用高度。软键盘弹出时把当前输入滚入可视区，不让底部保存栏盖住输入。

楼宇过滤、选择、批量记录仍由 `App`、`useWorkspace` 和 `BuildingDetail` 负责，不放进抽屉组件。`App` 只向抽屉发出「开始记录时展开」「保存后回半屏」等界面意图。

#### 楼／层／单位与记录的上下关系

采纳「当前位置在中间、记录在下面」的方向，但不让两个长区域同时固定挤在一屏：

1. **半屏选户阶段**：中间是楼／层／单位详情和立面，下方是当前选中户摘要及「記錄今次結果」入口。当前楼／层／单位用紧凑面包屑或摘要保持可见，多选 chips 放在记录入口上方。
2. **开始写记录**：自动上拉到 `expanded`，用户不用再拖一次。顶部只保留一个紧凑 sticky 上下文块：当前楼／层／单位、「更改」入口，以及批量模式下的已选户 chips 和逐户取消；它们属于同一块，不把批量选中户另放成独立区域。中间主体直接是记录表单，底部是保存／取消操作栏。
3. **表单滚动**：楼／层／单位选择与长表单不做成两个独立滚动容器。写记录时表单是唯一主滚动区，顶部上下文和底部操作栏保持可达，避免嵌套滚动和双重 sticky。
4. **收起不清草稿**：拖动收起、点地图空白或切到半屏只改变展示，不卸载 `ObservationEditor`，不丢未保存输入。重新展开回到原记录和滚动位置；真正取消／提交仍走现有表单逻辑。
5. **保存后继续下一户**：成功后回半屏详情档，保留当前楼／层和详情滚动位置，在表单上方显示内联保存状态；下一户入口立即可点。批量保存仍按需求 2 清理本批选择。
6. **桌面不变**：以上只改变手机排列和抽屉档位，桌面继续使用原有详情与编辑器布局。

### 3.2 共用数据路径

```text
snapshot.buildings + query + filter
              │
              ▼
   本地 search/filter 纯函数
              │
       filteredBuildings（唯一结果）
          ┌───┴────┐
          ▼        ▼
       楼宇清单    MapScene
                   └─ 周边弱化／目标描边，不改业务状态颜色

选择清单／地图 marker
          │
          ▼
workspace.selectBuilding(building.id)
          │
          ▼
同一 selectedBuildingId → 地图聚焦 + BuildingDetail
```

```text
触控多选 → chosen unit ids → 现有 ObservationEditor(batch)
                             → 每户生成一个 observation id
                             → 现有 recordBatch 一次本机写入
                             → 既有同步队列
```

### 3.3 保存状态路径

保存成功提示必须分为两个阶段：

```text
本机 repository 写入成功
  → 「已存在這台裝置」
  → 无服务器：「同事暫時看不到」
  → 有服务器：「等待同步／同步中」
        │
        ▼
RemoteWorkspaceRepository.save 返回新版本
  → 当前修订仍未再改变，且仍属同一工作区代次
  → 「已同步，其他裝置可在下次拉取後看到」
```

服务器 409 后重试、403 拒绝、冲突待选择和网络失败都不能显示「其他设备可以看到」。

## 4. 分项实施方案

### 4.1 需求 1：打开就是地图，需要时拉出清单

**要改的文件**

- `src/app/App.tsx`
- `src/styles.css`
- `src/refinement.css`
- `src/layout.css`
- `src/map/MapScene.tsx`
- `src/map/map.css`
- `src/components/ObservationEditor.tsx`（只调整手机承载与滚动，不改业务校验）
- 可新增 `src/components/MobileSheet.tsx` 和对应测试

**怎么实现**

1. 手机 `.app-shell` 改为视口内布局，主工作区 `position: relative; min-height: 0; overflow: hidden`；移除手机地图固定 400–460px 的做法，让地图占满工作区，底部只预留收起档把手高度。
2. 清单、详情和记录放进同一个三档底部抽屉，不再参与把地图向上推的文档流。实现 `collapsed`（约 64px）、`half`（约 50–55dvh）、`expanded`（工作区可用高度约 90–92%，并扣除顶栏与安全区），具体高度由真机验证微调。
3. 把手有可见小箭头和至少 44×44 CSS px 的触控区域；拖动跟手，松手按距离／速度吸附。点按箭头也能逐档展开或下降，不能只支持手势。半屏可继续上拉到近乎全屏，写记录时自动进入 `expanded`。
4. 抽屉滚动容器使用 `overflow-y: auto; overscroll-behavior: contain`，只滚当前内容；地图保持原相机中心、缩放和旋转。手势只绑定把手和非交互标题区，避免与清单滚动、单位点选、输入框和地图手势冲突。
5. 从地图 marker 或清单选择楼宇后，抽屉进入半屏详情档：上方是当前位置与选户、下方是记录入口；继续选楼／层／单位不重置抽屉或滚动位置。开始记录后压缩为顶部 sticky 上下文块，统一放当前位置、「更改」和批量选中户；下面只保留一个表单主滚动区，保存／取消在底部 sticky 操作栏。不得同时制造表单和详情两个长滚动区。
6. 移除「有 snapshot 就强制 `setFinderOpen(false)`」的效果。抽屉开合不得重建 `MapScene` 或卸载未提交的记录编辑器，也不得清空 `query`、当前楼宇、当前楼层、已选单位、表单草稿和各区域滚动位置。
7. `MapScene` 增加可选的空白点击回调。只有未点中业务楼宇／楼层、未操作轮廓编辑、未处于新增大厦流程时才收起；marker 点击仍只选择该楼。收起有草稿的记录时只隐藏，恢复后仍是原记录。
8. 清单、详情与记录由 `App` 统一协调同一个抽屉，不出现两个抽屉互相遮挡。保存成功后回半屏详情档，保留楼／层与详情滚动位置，让下一户入口立即可见。
9. 抽屉尺寸变化后通过现有地图尺寸监听／`map.resize()` 纠正画布尺寸，但不借 `resize` 重置相机。软键盘弹出时保证当前输入和保存操作可见。
10. 地图或 WebGL 不可用时，清单和录入仍可展开使用，不能把唯一入口绑在地图成功加载上。

**验收**

- 360px 和 390px 宽打开首页，地图占大部分，底部有清晰清单入口和向上箭头。
- 点箭头或上拉把手可从收起到半屏，再上拉到近乎全屏；松手吸附稳定，反向下滑逐档收回，不要求用户精确拖到某个像素。
- 清单滚到第 15 幢时地图画面不动；在清单内滚动不会误拖抽屉，在把手上拖不会误滚清单。
- 点清单楼宇后，地图和详情指向同一幢；半屏显示当前位置与选户、下方记录入口，开始写记录后自动近乎全屏展开。
- 写记录时当前位置摘要、批量选中户（如有）、当前输入和底部保存操作可达；批量选中户与当前位置同属顶部上下文块，不另占独立面板；收起再展开不清草稿，保存后回半屏并能立刻选下一户。
- 点地图空白处抽屉收起，再展开仍是刚才的档位、内容和滚动状态；不新增楼宇、不改变选择、不重置地图，桌面原有浮动布局不变。

### 4.2 需求 2：手指多选、逐户核对、一次记录

**要改的文件**

- `src/components/BuildingDetail.tsx`
- `src/components/UnitPickerBar.tsx`
- `src/components/unitSelection.ts` 及测试
- `src/components/UnitPickerBar.test.tsx`
- `src/app/App.tsx`（仅核对现有批量入口，不重写保存）
- `src/styles.css`／`src/refinement.css`

**怎么实现**

1. 在楼层立面提供可见的「多選」开关。未进入多选时，点一户仍走现有单户流程；进入后，连续点 A、B 使用现有 `nextSelection(..., true)` 累加，再点已选户即取消。桌面 Shift 路径保留。
2. `picked` 不再取决于 `chosen.length > 1`。多选模式下即使只有一户，也要有明确的勾选／描边和 `aria-pressed`；当前详情户与批量选中户使用不同视觉语义。
3. `UnitPickerBar` 从只收 `count` 扩展为接收 `{ id, label }[]` 和 `onRemove(id)`，显示「已選 2 戶：11A、11B」的 chips；每个 chip 有独立移除按钮和可访问名称，另有全部清除。
4. 多选模式下批量按钮只在至少一户时可按；点击后抽屉自动进入近乎全屏的记录档，顶部 sticky 上下文块同时容纳当前楼／层／单位、「更改」入口和选中户 chips，下面直接是批量表单，不另设批量选中户区域。保存前对话框继续列出批次数；保存成功后清空本批选择并回半屏详情，保留楼宇和楼层，便于继续下一批；是否停留在多选模式保持稳定，不因一次保存随机切换。
5. 继续使用 `pruneSelection`，结构变化后移除已不存在的单位 id；劏房父容器不进入当前可走访户的批量清单。
6. 继续使用 `App.saveObservation` 已有的逐户 id 和 `recordBatch`：每户各一条记录、同一次本机写入，其他户不变；批量表单仍不提供单户专属跟进字段。
7. 删除选中单位仍走现有管理员权限、备份与确认流程，本次只调整选择交互，不放宽任何结构删除权限。

**验收**

- 触屏不用 Shift、不用长按即可选 A、B，保存前明确看到两户名称；可只取消 A，B 仍在。
- 保存后 A、B 各新增一条相同结果记录，C 的历史和状态不变。
- 不进入多选时，单户点选和记录流程与原来一致。
- 鼠标、键盘和屏幕阅读器仍能辨认选择状态；触控目标建议至少 44×44 CSS px。

- `src/map/mapModel.ts`

### 4.8 需求 9：本机保存与跨设备同步状态一致

**要改的文件**

**怎么实现**

1. 在 `useWorkspace` 增加明确状态，而不是从 `account.workspace` 猜保存结果。建议包含：
   - `syncMode: 'local' | 'remote'`（是否确有已配置、已解锁的远端 repository）；
   - `syncStatus: 'local-only' | 'pending' | 'syncing' | 'synced' | 'error' | 'conflict'`；
   - `localRevision`、`confirmedRevision`、`lastSyncedAt`；
   - `workspaceGeneration`／账号与机构代次，用来拒绝旧工作区的迟到响应；
   - 现有 `storageError`、`pendingConflicts` 继续提供具体原因。
2. 每次本机 repository 真正写入成功后递增 `localRevision`，先显示本机已存；`localStorage` 抛错时不得出现任何保存成功。同步关闭、未设密语或未解锁时显示「已存在這台裝置，同事暫時看不到」，不能显示跨设备可见。
3. 有远端时置为 `pending/syncing`。每次 `push` 捕获正在发送的修订号和工作区代次；只有 `RemoteWorkspaceRepository.save` 返回新版本后，才把该修订记为 `confirmedRevision` 并记录时间。
4. 若等待服务器期间又发生本机编辑，`localRevision > confirmedRevision`，状态继续保持待同步；前一次写入成功不得把后一次未同步编辑也标成已共享。账号／机构切换后，旧代次响应不得更新新工作区。队列中的下一次写入成功后再更新。
5. 409 只在 pull → merge → retry 最终成功时算确认；403 仍按现有规则回退到服务器确认版本并说明权限原因；冲突、网络失败、413 和其他 HTTP 错误分别保持现有语义，不显示共享成功。
6. 账号／机构切换、导入、结构修改、撤回、强制推送、采用远端等所有写入路径都要检查状态重置，不能只给 `saveObservation` 单打一个补丁。
7. 保存反馈按状态显示：
   - 本机：「已存在這台裝置，同事暫時看不到」；
   - 远端等待：「已存在這台裝置，正在同步，其他裝置尚未保證可見」；
   - 当前修订已确认：「已同步，其他裝置可在下次拉取後看到」；
   - 失败：「已存在這台裝置，但尚未同步」＋具体原因／下一步。
8. 顶栏区分「功能已开启」与「本次已同步」；帮助和 `AccountPanel.featureText.workspaceSync` 改为「开启、设好机构密语、本装置解锁且同步成功后，其他装置才能在下次拉取后看到」，并说明约 30 秒／重新聚焦拉取是传播延迟，不是保存即全端可见。
9. `clearWorkspace` 另处理异步远端 DELETE：本机已清空不等于账号端和所有同事端已清空；只有 DELETE 成功才显示远端清空成功，失败和冲突保留明确状态。不得把普通 observation 的 PUT 成功状态套到 DELETE 上。
10. 不改变现有加密边界、服务器逐条权限判定、冲突合并和半分钟拉取策略；本需求预计不需要新增服务器 API。

**验收**

- 同步关闭时，本机刷新后仍有记录，换设备不可见，界面明确说明只存此设备。
- 同步开启但尚未解锁、同步中、断网、409 重试中或冲突时，都不能出现「其他设备可以看到」。
- 用可控 deferred PUT 模拟保存 A 后立即保存 B：A 的服务器响应不能把 B 标为已同步；B 也确认后才显示当前已同步。切换账号／机构后，旧响应不得污染新工作区；`localStorage` 写失败不得显示成功。
- 服务器确认成功后显示其他设备可在下次拉取后看到；帮助、顶栏和保存提示口径一致。
- 清空工作区用 deferred DELETE 单独验收：远端未确认前只说本机结果，成功／失败文案不得虚报所有同事端已清空；保留现有 403 回滚、500 保留本机、413 和合并冲突测试。

## 5. 邮箱验证：独立项目，不夹进手机适配 PR

需求已经明确「方案待讨论」，所以本计划不替团队决定发信商和验证政策，也不在本轮新增账号库字段。

### 5.1 开工前必须定案

1. **触发时点**：首次激活、更换邮箱、重设密码，还是全部都需要？
2. **旧账号策略**：全部视为已验证、下次登录补验，还是按机构分批处理？未验证是否允许继续使用？
3. **验证形式**：一次性链接还是验证码；有效期、重发间隔、尝试次数、链接失效后的处理方式。
4. **发信服务**：供应商、域名与 SPF／DKIM／DMARC、地区与资料条款、失败重试、费用和运维负责人。
5. **改邮箱流程**：先验证新邮箱再替换，还是替换后限制功能；原邮箱是否收到通知。
6. **隐私与审计**：邮件内容、token、邮箱地址和请求日志分别能记录什么；一次性链接不得进入公开 prompt 日志。

### 5.2 决策后再写的技术设计

预计会涉及 `server/` 的账号库迁移、邮件适配器、限时且单次有效且只存散列的验证凭证、限流与审计，以及 `src/auth/` 的待验证／重发／成功／失败页面。邮件 key 只能放服务器环境变量，浏览器不直连供应商。

验收至少覆盖：成功验证、过期、重复使用、重发使旧凭证失效、错误邮箱处理、发信失败、频率限制、旧账号迁移和权限不被绕过。完成这些决策前，邮箱验证保持独立排期，不作为手机版适配的验收前置条件。

## 6. 测试与验收安排

### 6.1 自动化测试

- **纯函数**：楼宇搜索规范化与过滤、选择增减与 prune、三档抽屉吸附／状态转换、同步修订状态机。
- **领域回归**：`UNKNOWN` 与 `NOT_UPDATED`／`NO_INDICATION` 的差别；劏房父容器排除、记录继承、有效记录和跟进；现有颜色语义不变。
- **组件**：抽屉箭头与按钮等价操作、手势不抢清单滚动、记录自动展开与草稿保留、多选 chips 和独立移除入口、`aria-pressed`、搜索命中 marker、保存状态文案、新增面板重选摘要。
- **地图模型**：搜索强调不改状态色；过滤输入不错误触发选楼；相机只在明确选择／全览时变化。
- **同步**：本机成功、远端待同步、成功、连续两次写入、403、409、冲突、断网、账号／机构切换、localStorage 写失败，以及 `clearWorkspace` 的 deferred DELETE。

现有测试若断言的是旧交互文案（例如只支持 Shift），应随新需求更新；若断言的是领域不变量，不得为了让实现通过而放宽。

### 6.2 手机与桌面手工验收

至少记录以下视口：

- 360×800：需求规定的最小宽度完整流程；
- 390×844：常见手机，检查抽屉、长楼名、软键盘和安全区；
- 桌面约 1280px：确认现有布局、Shift 多选和面板未回退。

建议至少在一台 iOS Safari 和一台 Android Chrome 真机走核心流程；若当期只能使用桌面设备模拟，须在 PR 明确写出未覆盖的真机，不把模拟器称为真机验收。

核心手工脚本：

1. 打开地图 → 点箭头到半屏清单 → 上拉到近乎全屏 → 下滑回半屏 → 滚到第 15 幢 → 选楼 → 收起抽屉 → 再展开，核对档位、地图和滚动位置。
2. 搜索「第三街100號」等四种写法 → 核对地图目标 → 打开同一真光大厦。
3. 新增大厦 → 选错 → 重搜重选 → 在 360px 核对名称／地址／位置 → 保存。
4. 多选 11A、11B → 单取消一户 → 再选回 → 点批量记录自动展开 → 批量保存回半屏 → 立即记录下一户。
5. 单户开始记录 → 收起再展开核对草稿 → 弹出软键盘并滚到备注／跟进 → 核对当前位置、输入框与保存按钮均可见 → 保存。
6. 无人应门 → 选「未能完成探訪」＋「今次未能判斷住房情況」→ 保存 → 查历史。
7. A 拆 A1／A2 → 完成 A1 → 核对地图和楼层总数 4、完成 1、剩 3 → 查原 A 历史。
8. 分别在同步关闭、等待、失败、成功后保存，核对每台设备可见性与界面文案。

## 8. 非目标与风险控制

- 不做原生 App、PWA 离线同步或新的离线队列；仓库约定仍明确排除离线同步。
- 不把首页本地搜索扩展成通用地理编码，不新增 Google／ALS 数据路径，不保存搜索原文。
- 不因同名、同地址或搜索命中自动合并楼宇；疑似重复仍按现有空间与人工核对规则。
- 不改变员工「能改不能删」、管理员权限、记录撤回、追加更正和敏感字段加密规则。
- 不为手机复制一套 `getCoverageSummary`、`currentAssessment` 或 `recordBatch`。
- 不用隐藏按钮代替服务器权限，不用成功 toast 代替服务器确认。
- 不做多个同时可拖的浮动面板，也不在清单和表单上全局拦截 touch/pointer 事件；只提供一个三档抽屉，并为所有手势提供按钮等价操作。
- 抽屉和地图联动要防止四类回归：地图被重挂载导致位置丢失、手势与滚动冲突、收起导致未保存草稿丢失、旧异步搜索／轮廓覆盖新选择；同步旧响应把新编辑标成已共享则由需求 9 的状态机防止。
- 手机布局不能成为唯一录入路径；地图失败时清单与表单仍应可用，桌面现有路径仍须回归。

## 9. 完成定义

只有同时满足以下条件，才算本轮手机适配完成：

- 需求 1–9 各有对应实现和可重复验收步骤；
- 360px 可完成找楼、重选新增地点、多选记录和下一户连续录入；
- 抽屉可用箭头或手势在三档间切换，写记录自动近乎全屏，软键盘下当前位置、当前输入和保存操作可达，收起不丢草稿；
- 清单、地图、详情使用同一楼宇选择与搜索结果；
- 劏房统计和住房判断在地图、详情、历史与领域规则中口径一致；
- 所有「其他设备可见」表述都有当前修订的服务器确认依据；
- 五项 CI 命令按实际结果通过，手机与桌面手工验收有记录；
- 邮箱验证保持独立项目，其待决策事项未被本计划擅自定案。
